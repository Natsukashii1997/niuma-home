# 04 · 旧数据迁移映射 `migration-v1.2`

把旧版用户情况（7 地区 × 6 格，见旧版 `docs/用户策略规范.md` 第 4 节）迁移到 Schema v2。

## 1. 迁移范围

| 数据 | 位置 | 数量 |
|---|---|---|
| 内置用户情况 | `docs/用户情况/2026-01.json` … `2026-12.json` | 12 个月 |
| 本地已修改的月份 | 数据库 `v3_documents`（kind `user-strategy`，id 为月份） | 迁移时实查（2026-11-07 时 11 月为「已修改」） |
| 已生成的促销策略 | 上面两处记录里的 `strategy` 字段 | 实查 |

## 2. 基本原则

1. **可信度只能保持或降低，不能抬高。** 旧内容没有链接到 Evidence ID，迁移后一律不能是 `known`。
2. **不编造新判断。** 旧版没有的字段（如购买准备度），迁移后是 `unknown`，不是推一个值。
3. **「你写的」原样保留**，`origin=manual`，正文一个字不改；可信度按第 3 节降为 `inferred + weak`（作者明确，不等于依据已追溯）。
4. **结构对不上的内容进 `legacy` 只读存档**，页面可以查看，不进入新对象，不参与校验和匹配。

## 3. 来源标注 → 状态与强度

| 旧来源 | status | evidenceStrength | limitations |
|---|---|---|---|
| 时间线 | `inferred` | `partial` | 「旧版引用，未链接到具体证据」 |
| 规则推导 | `inferred` | `weak` | 「旧版规则推导，对照表未成表」 |
| AI 判断 | `inferred` | `weak` | 「旧版 AI 判断，无外部证据」 |
| 推测 | `inferred` | `weak` | 「日期或事实未经确认」 |
| 原声 | `inferred` | `partial` | 「旧版原声引用，未链接到具体证据」（现有数据里没有这类条目） |
| 你写的 | `inferred` | `weak` | 「常浩写的，依据未追溯」；`origin=manual`，正文不动 |

**障碍例外**：旧 `A2` 换算成 `BR-M2` 后，按 [02-障碍体系v2](02-障碍体系v2.md) 第 2.3 节，只有节点位置、没有用户决策行为证据时只能是 `unknown`（不是上表的 `inferred + weak`）：`evidenceStrength=none`，gap 写「旧版 AI 判断，只有节点位置，缺少用户决策行为证据」（「你写的」写「旧版常浩写的，…」），route `{ status: available, source: SRC-bizcard }`，正文不动。这是降级，符合第 2 节原则 1。`BR-M5` 同理（旧数据里没有）。

1.2 三栏（common / diff / external）的条目也带 `origin`（`migrated` 或「你写的」对应的 `manual`），用于逐字核对和保护常浩写的内容。

迁移出的 Claim 都是 `origin=migrated`（「你写的」除外），`refVersions` 为空。批 1 上线后第一次 refresh，会把能对应上的条目链接到 Evidence，对应不上的保留原状。

## 4. 字段映射

| 旧字段 | 新位置 | 规则 |
|---|---|---|
| `summary.judgement` | `brief.judgement.text` | 原文保留；`claims` 为空 |
| `overview.common` / `diff` / `external` | `brief.common` / `diff` / `external` | 每条按第 3 节换算 status 与强度 |
| `overview.tiers` | `regions[].priority` | `value` 取旧分档；`default` 按 05 第 7 节矩阵重算（活跃度未知时为空）；`reason` 取旧依据。新 `other` 地区例外，见 5.1 |
| `overview.markers`、`lanes`、`counts` | 不迁移 | 由代码从当前时间线重算 |
| （无） | `regions[].activity` | 迁移时由代码按 05 第 6 节、用当前时间线计算 |
| `regions[].tier` | 同 `overview.tiers` | 两处不一致时以 `overview.tiers` 为准，并记入差异报告 |
| `regions[].temp` + `tempNote` | 一条 `need_strength` Claim | `level` 按旧温度的终点换算（冷 → 低、温 → 中、热 → 高）；`text` 写「原需求温度：温 → 热；」加 tempNote 第一条原文；status、强度按 tempNote 第一条的来源换算。tempNote 第二条起进 `legacy.regions[旧地区].tempNote`，只读存档 |
| （无） | 每个迁移情境一条 `readiness` Claim | `targetRelation=新签`；`status=unknown`；gap「旧版未区分购买准备度」；route `{ status: unavailable, source: SRC-crm, reason: "没有购买行为数据" }` |
| `regions[].node` | `legacy.regions[地区].node` | 只读存档。新版「关键节点」由 Evidence 投影，旧文字无法可靠对应到具体证据 |
| `regions[].task` | `task` Claim | 每条一个 |
| `regions[].pain` | `pain` Claim | `painKind=typical`（旧版没有观察证据） |
| `regions[].barrier` | `barrier` Claim | `barrierCode` 按第 5 节换算；`targetRelation=新签`（旧版障碍都是针对潜在新用户写的）；旧版列在第一条的为 `barrierRole=primary`，其余 `secondary`（I-11 要求恰好一个主障碍；旧版没有主次，取列出顺序） |
| `regions[].opp` | `legacy.regions[地区].opp` | 只读存档，不生成 Opportunity：旧版地区机会点没有优先级，不能编造 |
| `regions[].master` | `legacy.regions[地区].master` | 只读存档，全部保留。旧版硕士内容多为「推测」，自动识别成任务不可靠，以保护原意为先；该地区重新研判时，再由研判转成研究生情境下的 `task` Claim |
| `opportunities`（机会收敛表） | Opportunity | `priority`、`name`、`line`、`window`、`rationale` 照搬；「新签 / 续费」→ `通用`；`claims` 为空；`toulmin` 为空；Opportunity 在批 2 实现前，先存进 `legacy.opportunities`（编号 `OPP-<月份>-<序号>`；旧「地区」列原样存为 `regions` 文字，`window` 原样存旧窗口文字，批 2 生成正式 Opportunity 时再结构化） |
| `appendix.pending` | `research.notes` | 原文保留 |
| `appendix.guesses` | 不迁移 | 由代码重算 |
| `strategy`（旧促销） | `legacy.promo` | 只读存档，整段保留；与新方案对比时标「不可比较」 |

## 5. 地区与障碍换算

### 5.1 地区

| 旧地区 | 新地区 | 情境生成 |
|---|---|---|
| uk / us / hk / au / ca | 同名 | 每个地区生成一个迁移情境 `SCN-<月份>-<地区>-01`：`countries` 为该国，`targetRelation=新签`，`observedRelation.value=unknown`，`phase` 和 `keyTask` 取旧 task 第一条，`evidenceRefs` 为空（Scenario 的 `evidenceRefs` 必填要求对迁移情境放宽，见第 6 节） |
| sg | other | 生成 `SCN-<月份>-other-01`，`countries: ["sg"]`，旧 sg 的全部内容挂在这个情境下 |
| other | other | 生成 `SCN-<月份>-other-02`，`countries: ["nz", "mo", "ie", "my"]`，旧 other 的内容挂在这里 |

`legacy.regions` 按**旧地区 key**（`uk` … `ca`、`sg`、`other`）存放，每个旧地区一份 `{ name, tier, node, opp, master, tempNote }`，条目保持旧版 `[正文, 来源]` 原样；旧 sg 和旧 other 不合并，页面在新「其他」下同时展示两份。

新的 `other` 地区的策略优先级**不取旧两档中的任何一档**：
- 旧 sg、旧 other 的分档和依据完整存进 `legacy.regions.other.tiers`（`{ sg: { value, reason }, other: { value, reason } }`），页面可以查看。
- 新 `other` 的 `priority.value=null`，`reason` 写「待研判：由旧 sg 与旧 other 合并，旧分档见 legacy」，由 v2 研判重新产生。
- 差异报告里列出合并前的两档。

### 5.2 障碍编码

| 旧编号 | v2 编码 |
|---|---|
| A1 | `BR-M1` 没意识到需要 |
| A2 | `BR-M2` 觉得还来得及 |
| A3 | `BR-M3` 不信任辅导效果 |
| A4 | `BR-M4` 有替代方案 |
| B1 | `BR-C1` 嫌贵 |
| B2 | `BR-C2` 怕选错 |
| B3 | `BR-C3` 没时间 |
| B4 | `BR-C4` 需要家长同意 |
| C1 | `BR-O1` 没被触达 |

旧数据里只有 A1–C1，迁移时一一对应，不会映射到续费专属或新增障碍。

## 6. 迁移数据的校验放宽

迁移出的 revision 标 `migrated: true`，只在以下四处放宽：

1. 迁移情境的 `evidenceRefs` 允许为空。
2. `brief.judgement.claims` 允许为空。
3. `legacy` 字段允许存在。
4. `regions[].priority.value` 允许为 `null`（`reason` 必须写「待研判」及原因，Schema 第 4 节）。

其余不变量照常校验。月份第一次经 skill 生成新 revision 后，放宽自动失效。

## 7. 五步迁移

| 步 | 做什么 | 留下什么 |
|---|---|---|
| 1 | 冻结 Schema v2 与本映射（版本号写进迁移脚本） | 脚本里的版本常量 |
| 2 | 备份：12 个内置 JSON、`v3_documents` 里 kind 为 `user-strategy` 的全部记录、数据库文件 | `~/Library/Application Support/NiumaHome/evidence/<目录>/` 下的备份和清单 |
| 3 | 在隔离数据目录运行迁移，生成差异报告 | 每个月一份报告：条目数前后对比、状态换算明细、进入 legacy 的内容、tier 不一致项 |
| 4 | 验证 | 自动检查：条目总数守恒（新对象 + legacy = 旧条目）；没有 `known`；「AI 判断」「你写的」为 `inferred + weak`（第 3 节障碍例外为 `unknown`）；`manual` 正文逐字一致；新 `other` 的 priority 为 null 且旧两档在 legacy；校验器 0 错误 |
| 5 | 切换：把迁移 revision 写进正式库（须常浩看过第 3 步报告并同意）；旧版记录不动、只读存档；页面改读 v2 由策略页（1d）完成；写出可执行的回退命令 | 回退命令写进批 1 的 PR 和 `docs/OPERATIONS.md`；脚本 `scripts/migrate-strategy-v2.mjs` |
