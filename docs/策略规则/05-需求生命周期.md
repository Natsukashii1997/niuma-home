# 05 · 需求生命周期 `lifecycle-v0.2`

把单个学业事件，升级为一段连续的需求生命周期，支持跨月研判。本文所有天数都是**候选启发式参数**，用于方法论试运行，不是已验证的留学生需求规律，也不能当作购买概率或触达规则。

## 1. 五个字段

以事件锚点日期 T 为基准：

| 字段 | 定义 |
|---|---|
| `event_date` | 时间锚点：官方确认或有效推测的事件时间 |
| `need_window` | 该事件可能引发相关学业需求的候选区间 |
| `action_window` | 学生适合开始安排相关支持的候选区间 |
| `service_deadline` | 具体服务仍有合理交付价值的条件；动态计算，不按事件类型写死（第 7 节） |
| `next_stage` | 事件之后可能衔接的下一项学业任务（状态转换，不是时间窗口） |

需求窗口和行动窗口可以重叠。

## 2. 事件类型 → 生命周期类别

时间线解析出的事件类型（`server/timeline.mjs` 的 `eventType`），按下表归入八类：

| 生命周期类别 | 时间线事件类型 | 原列名示例 |
|---|---|---|
| Final | Final | Final 时间、S1 Final时间、final考试(Exams T1)、Final Period、Summer考试 |
| 期中 | 期中 | Midterm时间、期中/midterm时间 |
| Essay / Report 截止 | Essay 截止 | 含 essay、论文 的列 |
| 补考 | 补考 | final补考、补考时间 |
| 出分 | 出分 | 出分时间、成绩公布、final出分 |
| 选课 | 选课 | 选课时间、S1选课时间开放、Spring选课开始、学期选课 |
| 开学 | 开学 | Semester 1学期开学、T1开始（教学）、Spring开始上课 |
| 假期 | Reading Week、期中假 | Reading Week、感恩节假期、圣诞假期、Spring Break |

其他事件（教学日结束、Instruction结束、Withdraw 截止、Census Date 等）不属于八类，**不生成默认窗口**，只作情境信息。研判时可以引用，但窗口须写理由，status 为 `inferred`。

## 3. 锚点类型判定

| anchorType | 判定规则 |
|---|---|
| `start` | Final、期中、补考、开学：取事件开始日。列名含「开始」「开放」的选课单日事件，也是 `start` |
| `deadline` | Essay / Report 截止：取截止日。选课事件只有列名**明确含「截止」**的才是 `deadline` |
| `period` | 选课期起止都已知：列名表示一段选课期（含「选课时间」「选课时间开放」「学期选课」等），且原格给出完整起止。锚点是这段区间本身，**不套用截止规则**：选课期结束不一定就是正常选课截止，不能把结束日当成截止日倒推窗口 |
| `release` | 出分：取实际成绩发布日；原格是区间时取开始日 |
| `end` | 只在策略明确需要以结束日为锚点时使用（例如考试持续多天、要判断考完后的出分衔接），须在 Claim 里写明 |
| `anchor_unknown` | 选课列名判断不出是开始、截止还是补退选截止，且原格只有单日；或其他判断不出锚点含义的情况 |

`period` 目前只用于选课。其他类别的原格即使是一段区间（如 Final Period），仍按上表各自的规则取锚点。

`anchor_unknown` 的事件不套用任何锚点规则：不生成精确窗口，只保留「该月有选课相关节点」的月度研判，等补充来源或人工裁定。

## 4. 默认窗口（T 为锚点日期）

| 类别 | need_window | action_window | next_stage |
|---|---|---|---|
| Final | T-42 至 T-1 | T-28 至 T-5 | 出分、学期衔接、可能的补考 |
| 期中 | T-28 至 T-1 | T-21 至 T-3 | 课程后续任务、Final |
| Essay / Report 截止 | T-28 至 T-1 | T-21 至 T-3 | 后续作业、反馈、考试 |
| 补考 | 公告日至 T-1，回看不超过 28 天 | 公告日至 T-3，按实际剩余时间调整 | 出分、后续修课 |
| 出分 | T 至 T+14 | T 至 T+10 | 复盘、补考或新学期规划 |
| 选课（`deadline`） | T-30 至 T-1 | T-21 至 T-2 | 课程确认、开学准备 |
| 选课（`period`） | 不生成 | 取选课期本身（起日至止日），status 恒为 `inferred` | 课程确认、开学准备 |
| 开学 | T-45 至 T+14 | T-30 至 T+7 | 课程适应、第一次重要考核 |
| 假期 | 不默认推出独立辅导需求 | 不默认设置购买行动窗 | 视下学期或其他真实任务而定 |

补充规则：

1. **补考**：公告日不知道时，以同一学校同一学期的出分日**作为公告日的替代锚点**（不是真实公告日）；出分日也不知道，就用 T-28 作为需求窗口起点。两种情况窗口 status 都是 `inferred`，并在 limitations 里写明「公告日未知」。不能在补考资格尚未确认时，推断所有学生都已进入补考需求期。
2. **出分**：是新的需求起点，但不假设所有学生需要同一种服务。出分日期以实际发布时间为准，不从 Final 结束日推导。
3. **选课**：`deadline` 锚点套用上表的截止前窗口；`period` 锚点的行动窗口就是选课期本身，不倒推截止前窗口，也不生成需求窗口；`start` 锚点只说明选课开始，不生成截止前窗口。
4. **假期**：是情境因素，可能影响可用时间和消费注意力。只有与开学、预习、考试等具体任务形成联系时，才产生机会。

## 5. 窗口生成条件

| 日期情况 | 处理 | 窗口 status |
|---|---|---|
| 确定日期（官网核实、人工裁定） | 计算窗口 | `known` |
| 原表日期（未核实、未标推测） | 计算窗口 | `inferred` |
| 原表标为推测、但有具体日期 | 计算候选窗口，带「假设」标识 | `inferred` |
| 只有月份 | 不计算精确窗口，只保留「该月可能有需求」，可以支撑月度候选机会（Schema I-07 ②） | — |
| `anchor_unknown` | 不套用锚点规则，不计算精确窗口；同样只能支撑月度候选机会 | — |
| `ambiguous` 或身份碰撞（`identityConflict`） | 不计算精确窗口，不作为 `known` 判断的依据（Schema I-18） | — |
| 多个冲突日期，尚未裁定 | 不输出单一精确窗口，等待裁定；需要时只给出覆盖全部候选日期的宽泛风险区间，标「冲突未决」，不能作为 Opportunity 或 Strategy 的窗口依据 | — |
| 学校覆盖不完整 | 写明覆盖率；「没有记录」不等于「没有需求」 | — |

原表日期只算 `inferred`：它来自人工维护的大表，未经官网核实，按来源登记表强度上限是 `partial`。

每个窗口都记录 `ruleVersion`（如 `lifecycle-v0.2/Final`）和 `status`。默认天数只能经方法论修订流程修改；对某个地区或学校的单次调整，写进 Claim 的 limitations 和 rule 里，不改本规则。

## 6. 候选行动窗口覆盖率（需求活跃度，当月）

衡量某地区当月有多少学校的**候选行动窗口**落在统计范围内。它是由日历推出来的覆盖率，不是已验证的实际用户需求，也不等于付费需求。Schema 里的字段仍叫 `activity`，页面上的「需求活跃度」指的就是本指标。

**计算**：
- 统计范围：目标月整月，加下个月前 14 天。
- 可计算事件：第 5 节中能计算出 `action_window` 的事件，含 `period` 选课；不含假期和其他类，不含只有月份、`anchor_unknown`、冲突未决、`ambiguous` 或身份碰撞的事件。
- 有效学校（分母）：该地区在当前时间线快照里**至少有一个可计算事件**的学校。
- 活跃学校（分子）：至少有一个可计算事件的 `action_window` 与统计范围重叠。
- 覆盖率 `ratio` = 活跃学校数 ÷ 有效学校数。
- 分级（候选阈值）：≥ 40% 为高；15%–40% 为中；< 15% 为低。

**区分两种「不活跃」**（写进 `coverage`，不能合并解读）：
- 有校历但窗口未覆盖 = 有效学校数 − 活跃学校数：日历上本月不在行动窗口里。
- 数据不足 = 时间线学校总数 − 有效学校数：没有可计算的事件，不知道本月情况。「没有记录」不等于「没有需求」。

**status**：
- 计算得出时恒为 `inferred`：覆盖率是推断，不是需求观测，日期质量再高也不升为 `known`。
- 有效学校数为 0（时间线里没有该地区学校，或全部不可计算）时，`value` 和 `status` 都为 `unknown`。
- 日期证据质量单独写进 `dateQuality`：参与计算的事件按 `verification`（verified / ruled / source / guess）计数，供阅读时判断可信程度，不改变 status。

**其他地区**：`other` 按全体计算覆盖率，同时在 `byCountry` 里保留各国的贡献（每国的学校数、有效学校数、活跃学校数、覆盖率），不让单个国家的数据掩盖其他国家。

**阈值校准**（批 1，用 12 个月数据）：从六个方面看，不以任何单一来源为「正确答案」：

| 维度 | 看什么 |
|---|---|
| 历史分布 | 各地区 12 个月的覆盖率分布；高、中、低各档的月份数是否合理，有没有全挤在一档 |
| 地区敏感性 | 同一阈值下各地区的差异，能否用学期制度解释 |
| 数据覆盖 | 有效学校占比低的地区和月份，标「覆盖不足」，不参与阈值判断 |
| 时间合理性 | 高覆盖月份是否与考试季、开学季等学期节奏吻合 |
| 阈值敏感性 | 阈值上下浮动（如 ±5 个百分点）时分档变化有多大；处在边界附近的月份单独列出 |
| 旧版对照 | 与旧版分档不一致的月份逐个查原因；旧版只作调查线索，不作正确答案 |

需要调整阈值或窗口天数的，走方法论修订流程。

## 7. 当月策略优先级的默认建议

策略优先级（主战场 / 次要 / 平稳）综合业务权重、需求活跃度、机会与产品匹配，由研判决定。下表只给**默认建议**，研判结论与默认不同时，`priority.reason` 必填。

默认矩阵只是初始参考：它不直接生成 P0 / P1 机会，也不决定促销主打法。迁移数据或暂时无法判断时，`priority.value` 可以为 `null`，`reason` 写「待研判」（Schema 第 4 节）。

| 需求活跃度 | 英国、美国 | 香港、澳洲、加拿大 | 其他 |
|---|---|---|---|
| 高 | 主战场 | 主战场 | 次要 |
| 中 | 主战场 | 次要 | 平稳 |
| 低 | 次要 | 平稳 | 平稳 |
| 未知 | 无默认，研判给出并写理由 | 同左 | 同左 |

业务权重、需求活跃度、策略优先级是三个概念，不能混为一谈：英国长期权重高，但某月澳洲可能需求更集中、更迫切；某地区学校事件多，也不能直接证明存在大量高价值付费需求。

## 8. service_deadline

由「学业事件 + 服务类型 + 最低交付要求 + 可用资源」计算。服务类型参数表（`SRC-service`）在批 2 建立。在此之前一律为：

```jsonc
{ "status": "unknown", "gap": "缺少服务类型与最低交付周期",
  "route": { "status": "unavailable", "source": "SRC-service", "reason": "参数表在批 2 建立" } }
```

批 1 只生成候选需求窗口和行动窗口；需要真实发布促销时，在批 2 结合服务条件校验截止时间。
