# 06 · SCOUT-8 运行规范 `scout-v1`

SCOUT-8 是月度用户策略的主运行流程，八种思维模型是这个流程的思考工具。本文规定每个阶段的输入、动作、输出、质量关口和缺失处理，作为 skill 编写和自检的依据。

## 1. 原则

1. **每一段只用上一段的结论**，不回头补信息；发现上游有误，回到上游修正后再往下走。
2. **内部严谨、外部清晰**：内部完成证据、推导、限定、反驳；正式稿只展示关键的依据、推理、条件和结论。
3. **允许未知，不许用未知掩盖分析不足**：已有来源但没检索，属于分析不完整。
4. **促销必须交付，但不强制生成无依据的主推**。

## 2. 八个阶段

### 阶段 01 · 事实取证

| 项 | 内容 |
|---|---|
| 目标 | 建立目标月可信的事实基础 |
| 输入 | 时间线 Evidence（含核验、裁定）；业务背景卡 Evidence；来源登记表；外部节点（当地消费节点、中国节点） |
| 动作 | 按 [05-需求生命周期](05-需求生命周期.md) 取出与目标月相关的事件（含回看与前瞻：任何需求窗口或行动窗口与目标月重叠的事件都算）；列出每个地区的数据覆盖率；列出日期冲突、推测、`anchor_unknown`、只有月份的事件 |
| 输出 | 关键事件清单（Evidence ID 列表）；各地区时间全景；事实不确定性清单；外部变量（`brief.external`） |
| 质量关口 | 事件、学校、日期、适用对象都有来源；预测不能表述为事实；核心考试日期冲突时，不使用未确认的日期 |
| 缺失处理 | 某地区没有事件：写明覆盖率，不写「没有需求」。时间线快照不完整：停止生成，提示先同步 |
| 思维工具 | — |

### 阶段 02 · 情境定位

| 项 | 内容 |
|---|---|
| 目标 | 确定这个月主要分析谁 |
| 输入 | 阶段 01 的事件清单；业务背景卡里的存量用户情况 |
| 动作 | 按「地区与学校 + 学业阶段 + 关键任务 + 目标人群」划分情境；合并任务、困难、时间窗相同的用户群；每个地区 1–4 个情境；硕士节点与本科明显不同时单列研究生情境 |
| 输出 | Scenario 列表 |
| 质量关口 | `targetRelation` 已设定；`observedRelation` 只有业务证据时才不是 unknown；不把一个地区的所有学生当成一个群体，也不为每所学校单独成情境 |
| 缺失处理 | 没有存量用户信息：续费情境的 `observedRelation=unknown`，续费研判按 [07-业务背景卡](07-业务背景卡.md) 第 3 节降级 |
| 思维工具 | 情境分群与用户旅程 |

### 阶段 03 · 需求解码

| 项 | 内容 |
|---|---|
| 目标 | 从时间节点推出用户的学业需求 |
| 输入 | Scenario；事件的需求窗口、行动窗口 |
| 动作 | 按「时间节点 → 待完成任务 → 学业困难 → 期望进展 → 潜在支持需求」推导；区分客观任务、典型困难、实际困难、潜在需求、已验证需求；判断学业需求强度；必要时用 Bloom 认知层次细化学业困难 |
| 输出 | `task`、`pain`、`academic_need`、`need_strength` 四类 Claim |
| 质量关口 | 考试存在只能证明有考试任务，不能证明学生普遍缺乏复习能力；没有反馈、诊断或记录的痛点只能是 `typical`；需求强度引用的窗口带规则版本 |
| 缺失处理 | 缺少真实反馈时，用克制的写法（例：「考试节点可能带动复习规划需求，尚需咨询及诊断证据验证」），status 为 `inferred` |
| 思维工具 | JTBD；Bloom（按需） |

### 阶段 04 · 决策洞察

| 项 | 内容 |
|---|---|
| 目标 | 判断需求为什么没有转化为购买行动 |
| 输入 | 阶段 03 的 Claim；业务背景卡；障碍体系 v2 |
| 动作 | 新签、续费分开研判；用 COM-B 判断卡在动机、能力还是机会，用 Fogg 判断触发与时机，有竞争或续费问题时用 Forces of Progress 分析替代方案、转换动力与阻力；判断购买准备度 |
| 输出 | `barrier`、`readiness` 两类 Claim |
| 质量关口 | 有依据才写障碍，没有依据就写 unknown 并附 gap、route；不为触发促销规则而创造障碍；续费不复制新签障碍；不默认老学员没有信任障碍；学业需求和购买需求不混淆 |
| 缺失处理 | 只有时间线、没有购买证据：障碍可以是 `inferred + weak`（写明推断依据和限定），或 `unknown`。不能是 `known` |
| 思维工具 | COM-B；Fogg；Forces of Progress |

### 阶段 05 · 机会收敛

| 项 | 内容 |
|---|---|
| 目标 | 从大量需求里找出本月重点 |
| 输入 | 阶段 02–04 的对象；各地区需求活跃度；业务权重 |
| 动作 | 用 OST 先定用户机会、再想解决方案；六维判断（时间相关性、用户需求、业务重要性、服务适配、商业价值、证据充分性）；定 P0 / P1 / P2；定各地区策略优先级（参考 05 第 7 节默认建议） |
| 输出 | Opportunity 列表；`regions[].priority` |
| 质量关口 | P0 / P1 写完整的 Toulmin 六要素；允许某地区没有 P0，没有证据不强造主战场；优先级与默认建议不同时写理由 |
| 缺失处理 | 证据不足的机会只能是 P2（待验证机会），并写明验证方式 |
| 思维工具 | OST；Toulmin |

### 阶段 06 · 策略设计（批 2 实现）

| 项 | 内容 |
|---|---|
| 目标 | 产出用户策略建议和促销策略建议，两者同等重要 |
| 输入 | Opportunity；barrier Claim；障碍 → 促销目标候选映射；打法库；服务类型参数表；`baseline-v1` 输出 |
| 动作 | 先写用户策略（围绕哪些人、哪些问题、哪些产品和服务方向）；再按「用户机会 → 购买障碍 → 促销目标 → 候选打法 → 适用校验 → 方案组合 → 专业论证」生成促销；每个目标提 2–3 个候选打法，过六个匹配条件（目标、用户、时间、产品、组合、业务边界）；新签、续费各自形成主推、辅助、特殊场景组合；记录与基线的差异 |
| 输出 | Strategy 列表；用户策略段落；每个主要策略附「部门协同关注点」一行 |
| 质量关口 | 时间适用性由规则校验（例如考试只剩几天，不推荐早鸟类打法）；「限时」必须有真实期限、容量或学习节点依据；「不采用」写实质理由；数量受必要性和执行复杂度约束，不凑数 |
| 缺失处理 | 按依据充分程度分级：依据充分 → 推荐；部分充分 → 附条件推荐（写适用信号）；关键判断缺失 → 候选待确认；明显不适用 → 不采用 |
| 思维工具 | Fogg（促销阶段）；Toulmin |

### 阶段 07 · 论证自检

| 项 | 内容 |
|---|---|
| 目标 | 定稿前挑战自己的策略 |
| 输入 | 完整初稿与研判记录 |
| 动作 | 检查 1：每个阶段完成时检查输入、输出、依赖和缺项（批 1 起）。检查 2：初稿完成后，由新上下文的子 agent 或跨模型做整份独立复审（批 2 起）。检查 3：返修后由同一复审方定向验收，只核上一轮指出的问题 |
| 输出 | 自检记录（[08-质量标准](08-质量标准.md) 第 3 节）；review 记录 |
| 质量关口 | 复审方拿到五项输入：正式稿、结构化研判记录、关键事实与来源引用、方法论与质量标准、规则和数据版本；不给生成过程。一次全面复审 → 一次返修验收 → 未解决的关键问题交常浩裁决，不无限循环 |
| 缺失处理 | 复审无法进行（例如没有可用的独立执行方）：自检记录标「检查 2 未执行」及原因，不能写成通过 |
| 思维工具 | Toulmin（反驳与限定） |

### 阶段 08 · 发布沉淀

| 项 | 内容 |
|---|---|
| 目标 | 形成正式稿，留下内部研判记录 |
| 输入 | 通过自检的内容 |
| 动作 | 按 [03-Schema-v2](03-Schema-v2.md) 第 4 节组装月度文档；生成 `idempotencyKey`；调用 `strategy_submit` 提交；在答复里给出预览入口，提醒常浩在页面确认 |
| 输出 | submission；正式稿（展示映射）；`research` 内部研判记录 |
| 质量关口 | 提交内容通过 Schema v2 全部不变量；不调用确认接口 |
| 缺失处理 | 提交被拒（结构错误、基础版本变化）：按错误修正后重新提交；结果不明时不自动重试，先查 submission 状态 |
| 思维工具 | — |

## 3. 四种运行模式

| 模式 | 用途 | 阶段 | 首次实现 |
|---|---|---|---|
| `generate` | 生成某月完整策略 | 01–08 | 批 1（01–05、08），批 2 补 06–07 |
| `refresh` | 日期或重要事实变化后更新已有月份 | 只重跑 `evidenceVersion` 变化所影响的 Claim 及其派生对象；`origin=manual` 的内容只标「依据已变化」，不改写；提交附受影响对象清单 | 批 3 |
| `review` | 对某份策略做独立复审 | 07 的检查 2、检查 3 | 批 2 |
| `refine` | 根据反馈和重复问题提出方法论修订 | 不跑阶段；读评级、复审记录和基准案例，产出认知深化提案 | 批 3 |

`review` 判断当前策略写得对不对；`refine` 判断产生策略的规则需不需要改。两者不混用。
