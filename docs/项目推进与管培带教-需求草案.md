## 3. 对现有工作的理解

### 项目推进管理

当前 3 个项目为两个产品项目和一个营销战役。项目表保存名称、类型、负责人、起止时间、关联任务／文档／物料、状态，以及模板和初始化信息。任务表进一步保存阶段、父子关系、主责任人、期限、完成标记、实际完成时间和交付物。

任务样本有“项目定义—问题树拆解—任务拆解／排期—调研—设计研发对接—验收与业务验证—结项复盘”等内容，也包含独立的审核节点、里程碑。营销战役样本则涉及立项、历史资产盘点、战役策略、内容生产、视觉物料与复盘。两类项目可以共享推进方式，具体节点仍需保留差异。

**分析判断：**核心工作是知道项目处于什么状态、接下来由谁完成什么、哪些节点需要判断或审核，以及证据在哪里。界面可以简化，负责人、期限、交付物与审核关系不能一并抹去。

现有视图包括按项目、看板、甘特图、截止日历和总表；仪表盘包括任务数、完成数、关键任务、执行人与分布、切片器等。工作台可把常用判断集中在一个入口，不要求用户先选择多种表格视图。是否保留甘特图等扩展能力仍待校准。

### 管培带教答疑

现有内容分为两类：问答记录保存具体问题、答案和处理状态；Q&A 合集承载整理后的知识内容，涵盖业务思考、调研、项目收敛和北极星指标等主题。

问答记录包含三组独立状态：

- **答案审核**：待生成、待审核、待改稿、已通过、已否决。
- **归档审核**：未提议、待确认、已批准、已否决。
- **实际写入**：未开始、执行中、待核验、失败、已查回确认。

本轮 13 条记录中，答案审核为 8 条已通过、5 条待审核；归档审核为 2 条已批准、6 条待确认、5 条未提议；实际写入状态均为已查回确认。待处理说明区分了“问答记录已同步”和“固定 Q&A 已完成两步审核并查回发布”。因此不能用一个“完成”状态替代这三件事。

**分析判断：**这里既有答疑处理，也有知识整理。工作台应帮助常浩查看问题与当前答案、决定是否通过或改稿，再独立决定是否适合进入知识合集；写入与发布结果由系统明确回报。是否新增自动生成答案或让管培生直接在工作台提问，尚未确认。

### 管培生日志与带教 Agent（用户新增）

**已确认：**接入胡贵兰、林瑶两人的日志，在日志旁提供带教 Agent，辅助常浩发现卡点、准备追问和反馈草稿。沿用个人工作台由常浩使用的现有范围；本次新增两位日志对象，不等于开放两位直接使用工作台。问答记录表与日志是独立来源，不自动混为同一对象。

**实际来源：**用户第一个链接标题为《林瑶-管培生日志》，第二个为《胡贵兰-管培生日志》，按文档标题核对归属，不按姓名或链接顺序猜测。两份均为持续追加的 Docx，日期加主题作为一级标题，目录顶部均为 10.14。林瑶样本含复盘、思考、后续动作、疑问／结论、产出及附件；胡贵兰样本含复盘、思考、产出、问题／结论、概述。两者都含表格与多级文字，不要求用户先改造成完全相同的模板。

本轮只读取目录与各一篇近期正文，用于核对结构，不作人员评价或完整带教诊断。历史接入范围、刷新方式、年份缺省与跨年日期规则、项目关联方式尚待细化；不能因目录顶部日期、缺少某天标题或部分空小节就推断未工作、未更新或没有产出。日志中的陈述属于作者自述，涉及实际交付／效果时仍需对应证据。

**建议的日常过程，待校准：**选择一位管培生与日期范围 → 阅读原始日志 → 在旁边向 Agent 提问 → 对照引用的日志核实分析 → 由常浩采纳为带教反馈或后续事项。建议可分别查看两人日志、按时间回看并打开来源；不依据姓名猜测文档归属，不把日志缺失当作没有工作进展。

**Agent 已确认职责：**结合日志发现卡点、准备追问与反馈草稿，供常浩带教使用。可提问“这段时间最需要我介入的是什么”“针对这篇日志下次怎么追问”。阶段进展汇总、跨期比较反复出现的问题、后续跟进建议为建议展开；不自动为管培生答疑或发送反馈。

分析应显示实际读取的人、日期范围和来源引用，将日志原话、事实摘要与 Agent 推断分开。选择单人时不自动混入另一人的内容；需要跨人汇总时明确范围，不据单篇日志做能力定性或绩效排名。既有 Q&A 或项目材料如需参与分析，应显式标明引用范围；不默认开放全知识库或其他个人资料。

用户暂未授权修改管培生原始日志或代发反馈。Agent 输出先作为建议或草稿；采纳到项目／答疑记录时沿用预览、确认、同步及回读。向管培生发送消息、知识归档与更新记录是不同动作，后续分别确定入口、目标和权限。

## 4. 建议的简化方式（待校准，不是正式页面或派单）

侧边栏保留用户指定名称「项目」，内部围绕两项工作组织：

| 区域 | 优先帮助用户完成什么 | 首层建议保留的信息 |
|---|---|---|
| 项目推进管理 | 扫一眼项目状态，定位近期节点和需要处理的事项 | 项目名称／类型、源状态、负责人、明确的期限、任务概况、待处理节点 |
| 项目详情 | 沿阶段查看任务和交付物，理解上下文再处理 | 可展开的父子任务、负责人、期限、完成记录、交付物入口、里程碑／审核节点 |
| 管培带教：日志与旁侧 Agent | 查看胡贵兰、林瑶的日志，辅助常浩发现卡点、准备追问和反馈草稿 | 两人来源与 Agent 职责已确认；建议显示人员、日期、原文／来源、读取范围和有引用的分析 |
| 管培带教答疑：待处理 | 对问题及答案做判断，找到待审核／改稿／归档事项 | 问题、当前答案、版本、答案审核、归档审核、待处理原因 |
| 管培带教答疑：知识合集 | 查找、阅读和复用已有内容 | 主题、问题、答案、来源、收录状态及需要核对的审核信息 |

- 日常先呈现业务信息，公式、关联表配置、模板版本、案件 ID 等收在详情或追溯信息中，不要求用户理解它们才能使用。
- 项目总览中的“需要我处理”“受阻”“下一步”必须有可靠状态、负责人或人工标注依据；目前字段没有完整提供这些语义，不能把未完成、超期或节点类型直接推断成特定人员待办。
- 子任务在需要时展开，交付物就近可见；先支持找准任务和判断状态。新建项目、批量分派、模板启动与自动催办不因看到原表能力就自动纳入第一版。
- 答疑可按处理状态、主题和关键词查找。用户已确认在工作台处理答疑审核并预览确认后同步；答案编辑、归档审批的具体字段、权限与流程仍需细化。知识合集的阅读与待处理记录分开，避免草稿被当作已批准答案使用。
- 项目中的问题可以按需引用知识合集；答疑也可保留相关项目入口。两者的自动关联能力尚未确认，不自行猜测归属。

## 5. 需要保留的数据与状态边界

1. **进度不等于业务验收。** 项目表的任务完成度是按任务勾选计算的比例；初始化完成只表示启动准备状态。二者都不能替代项目完成或业务效果判断。父子任务统计分母尚未全量核对，不直接重算或改公式。
2. **缺失值如实显示。** 本轮 3 条项目的“项目定义”和“项目截止时间”列均为空，不表示其他关联文档没有这些信息。不得自动生成目标或截止时间；后续可提示补充或引用来源。
3. **审核节点不等于审批记录。** 任务表有审核门禁类型和完成标记，但未见专门的审核人、审核结论与意见字段。若工作台要承接正式审核，须先明确数据和权限约定，不能仅勾选任务便声称审批完成。
4. **记录、答案审核、实际发送与知识发布分别核验。** 先确认更新了哪个对象，再核实结果。“已通过”或“已查回确认”不能证明答案已送达；发送结果需要单独核验，本轮未读取消息正文或发送回执，也未获得发送授权。答案版本变化后，旧的审核结论是否仍有效需有规则；不把旧批准自动套给改写后的内容。
5. **尊重已有多人更新。** 已确认后续回写采用预览确认：保留稳定来源关系，先预览差异、确认再提交，并逐项回读结果；源记录已经变化时重新核对，避免覆盖他人更新。失败或结果未知不能显示为同步完成；不承诺未经验证的跨接口单事务或自动回滚。本轮仅记录需求，未执行回写。

## 6. 本轮发现，待后续核查

- Q&A 合集中已存在“业务思考项目步骤”等内容，而对应问答记录的归档审核仍待确认。这证明当前两处状态不能机械等同；未追查历史发布流程，不将其定性为程序故障，也不修改任一方。
- 问答表含重复标题、卡片占位文字、混入其他业务输入的记录。只根据表内条目数不能当作有效问题数或真实待办数；后续需明确哪些记录应进入答疑视图。不能根据标题自动去重或删除。
- 任务表目录记录数、项目关联数量与父子任务的进度统计还未全量对账；本轮只做结构理解和有限抽样，不据样本判断整个团队进度、效率或个人表现。
- 仪表盘只读到元数据，部分类型显示 unknown；不代表组件坏了，本轮未做页面视觉和运行验证。

## 7. 已确认决定与待定项

**已确认决定：**用户选择在工作台更新任务进度、处理答疑审核，预览确认后同步飞书。新增胡贵兰和林瑶的日志及旁侧带教 Agent；两份来源已给出并核对标题，Agent 明确辅助常浩结合日志发现卡点、准备追问和反馈草稿。这些决定替代此前回写方式、日志来源和 Agent 职责待回答的状态，不重复询问。

**待整体细化：**日志历史范围、刷新节奏、带教记录的保存位置与跟进方式，以及 Agent 是否引用特定项目／Q&A 内容。当前无需为继续需求盘点重新询问已确认方向；后续确定首版范围时再补齐。

其他细化留待整体校准：项目更新的具体字段与审核权限、答案修改和发布流程、日志历史范围与更新方式、已有文档和记录的关联口径、异常记录的展示、刷新与冲突处理。不扩展为通用低代码表格、团队绩效系统或新的机器人自动化。

## 8. 候选验收场景

- 从「项目」入口找到真实项目，在不翻多张表的情况下，查看阶段任务、负责人、期限及交付物；能区分任务进度、初始化状态和业务验收。
- 找到一条待审答疑，理解问题、当前答案及待处理原因；处理时明确区分答案审核和知识归档，预览影响后确认同步，操作后可核对结果；来源有变更或同步失败时不误报成功。
- 分别找到胡贵兰与林瑶指定日期范围的日志，原文和来源可核对；旁侧 Agent 明示读取范围，卡点、追问与反馈草稿能定位到依据，缺失内容如实提示；由常浩校准后采纳，不以生成文字代替已完成带教。
- 查找一个知识主题，读到对应内容和来源；合集收录但审核状态待核对时明确提示，不伪装成状态一致。
- 不完整数据、过期来源、无权限、读取失败或写入结果未知有可见提示；不能显示成无待办或处理完成。

本轮产出为需求草案与来源结构判断，未形成正式技术方案、API 或开发派单。后续沿既有 Claude／Codex 分工推进，用户决定业务取舍并验收真实使用效果。
