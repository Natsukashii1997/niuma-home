要求（接口约定已写进 `docs/API.md`）：
- `POST /api/settings/:key/preview` 接受四键，请求 `{ value }`，按 T07/T05B 原有校验规则校验（`settingValue` 的规则不变，包括 `weekly_doc_url` 空串表示清空），返回与 V3 键同形状 `{ previewId, expiresAt, key, before, value }`。

- `weekly_doc_url` 清空：确认后删除该行，回读时该键不存在，回执 `{ key, value: "" }`。

### R2 · brief 附件删除与新增的文件/记录一致性（L02、L04）

现状：`server/brief-attachments.mjs` 的 `confirm()`：
- 删除分支先提交记录并缓存 `p.receipt`，再 `rmSync`；删文件失败后重试命中缓存，返回假成功（N09 已复现）。
- 新增分支先缓存 `p.receipt`，再做哈希回读；回读失败或读文件异常时，记录已写、回执已缓存，重试同样会返回成功（静态确认，未失败注入）。

要求：
- **只有文件和记录都处于目标状态并回读一致后，才缓存并返回成功回执。**任一步失败必须返回错误，且不留下「记录与文件不一致却报成功」的状态。
- 具体做法由你定，但必须满足：删除失败后，要么记录仍在（可重试删除），要么重试能真正清掉文件后再报成功；新增时哈希不一致或读文件异常，不能留下有记录无正确文件的附件，重试不能返回成功。
- 测试：N09 TODO 改为正式断言并通过；新增「新增后哈希不一致」「新增后读文件抛错」两个失败注入用例，断言 HTTP 状态、记录数、文件存在性和重试结果。
