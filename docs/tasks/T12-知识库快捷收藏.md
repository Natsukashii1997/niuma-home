### R2 · 收藏预览 `POST /api/v3/kb/collect/preview`

- 链接解析：只接受飞书文档链接（`/wiki/`、`/docx/`、`/sheets/`、`/base/`、`/slides/`、`/mindnotes/`，以及 `/file/`），不接受账号、端口、其他域名。其余一律 `400 COLLECT_URL_INVALID`。
- 用 `wiki +node-get`（按链接或 obj_token）解析原文档的标题、类型、`node_token`、`space_id`，以及所在位置名（知识库名或「我的文档库」）。
  - 读不到（无权限或不存在）：`404 COLLECT_SOURCE_UNREADABLE`，说明原因，不暴露原始错误里的敏感信息。
  - 不是知识库节点（云盘文档等）：在 R5 首跑验证前，一律返回 `422 COLLECT_SOURCE_UNSUPPORTED`，提示「这篇在云盘里，暂不支持收藏快捷方式」。**不得**为了收藏把原文档移进知识库。
- 查重：扫描目标空间全部节点（可分页、可短期缓存，但每次确认前必须重新核对），找出 `node_type=shortcut` 且指向同一原文档的节点。
  - 原文档本身就在目标空间里，也算「已在知识库中」。
  - 以上两种情况都返回 `duplicate`，并且 `confirmable=false`。
- 归类：用标题及原文档所在的上级目录标题做匹配（不区分大小写），按命中目录列出 `matched`。
  - 恰好命中一个目录：`chosen` 为该目录。
  - 命中多个或都没命中：`chosen=null`，交给用户选；都没命中时 `suggested` 给「杂项其他」，但仍须用户选定。
  - 请求带 `targetNodeToken` 时，以用户所选为准，但必须是规则表里的目录。
- 预览令牌 10 分钟有效，绑定原文档、目标目录和查重结果。

### R3 · 收藏确认 `POST /api/v3/kb/collect/confirm`

- `{ previewId, confirm: true }`。执行前重新核对：令牌有效、目标目录仍存在、仍未重复。
- 只调用一次 `+node-create`（快捷方式），**不自动重试**。随后用 `+node-get` 回读新节点，确认以下几点全部一致才返回成功：`node_type=shortcut`、父节点等于目标目录、指向的原文档等于预览中的原文档、所在空间正确。
- 同一令牌重复确认，返回同一份回执，不重复创建。
- 结果不明（命令超时、输出无法解析、回读失败）：返回 `502 COLLECT_RESULT_UNKNOWN`，并附操作记录 `receipt`。之后同一原文档的预览和确认都要先核对，可沿用 `kb/operations/:id/reconcile` 的做法。
- 操作记录存本地（沿用 `local-records` 或现有知识库操作记录），不新增表；记录原文档、目标、节点 token、时间、结果。

### R4 · 最近收藏 `GET /api/v3/kb/collect/recent`

## 7. 变更 · 2026-10-18（用户确认，覆盖上文冲突处）

用户不要快捷键，要和「数码宝贝世界」一样在页面上点一个按钮就收藏，并取消这一项的「先预览、后确认」。接口以 `docs/API.md`「知识库 · 快捷收藏（T12）」为准。

- **R2 + R3 合并为 `POST /api/v3/kb/collect`**：`{ url, requestId, targetNodeToken? }`。链接解析、云盘来源拒绝、查重、归类规则不变；归类改为自动定目录：唯一命中用它，多命中取规则表里排最前的，无命中用兜底目录（无关键词那一项）。查重命中返回 `status: "duplicate"`，不创建。原来的 `collect/preview`、`collect/confirm` 不再需要，不要实现。
- **幂等**：同一 `requestId` 只执行一次，重复请求返回同一结果（含结果不明的回执）；`requestId` 与操作记录一起存本地。
- **写入约束不变**：每次请求前重新核对目标目录存在、未重复；只调用一次 `+node-create`，不自动重试；回读一致（`node_type=shortcut`、父节点、指向原文、空间）才算 `created`；结果不明返回 `502 COLLECT_RESULT_UNKNOWN` 带 `receipt`，此后同一原文档的请求返回 `409 COLLECT_PENDING` 带 `receipt`，直到 `kb/operations/:id/reconcile` 核对。核对返回 `state: "verified"` 表示已建好。
- **R4**：`recent` 的 `status` 增加 `"duplicate"`。
- **R6 · 扩展配对码（新增）**：见 API.md「扩展配对码」。配对码 64 位小写十六进制，首次读取时生成并存数据目录；`Origin` 为 `chrome-extension://…` 的请求须带 `X-Niuma-Collect-Code` 且相等，否则 `403 COLLECT_PAIRING_REQUIRED`；其他外来 `Origin` 一律 403；同源或无 `Origin` 照常。`GET /api/v3/kb/collect/pairing` 只给本站页面；重新生成走 `pairing/preview` → `pairing/rotate`。不加任何 CORS 放行头。配对码不得出现在日志和错误信息里。
- **R5 测试补充**：同一 `requestId` 重复请求不重复创建；多命中取第一个、无命中走兜底；`COLLECT_PENDING`；扩展来源无码 / 错码 / 正确码；其他外来 Origin；配对码轮换后旧码失效；`pairing` 读取拒绝扩展来源。去掉针对 preview / confirm 两步的用例要求。
