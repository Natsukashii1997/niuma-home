### 1.3 我补充的 5 处工程细节（复审没覆盖，来自现有代码）

1. **事件没有稳定 ID。** 时间线事件现在只用「来源格」（如 `英国 爱尔兰!S12`）定位。Evidence ID 规定为「来源格 + 原文 + 片段序号」的指纹，与人工裁定、官网核验用同一套指纹规则。飞书原格一改，ID 就变，引用它的判断自动标为「依据已变化」。这正是 refresh 要找的东西。
2. **选课的锚点信息在解析时丢了。** 复审要求区分选课开始、正常截止、补退选截止。但现有解析把所有选课类列名都归成「选课」，事件对象也不保留原列名。批 1 要让事件带上原列名，再按列名细分锚点；分不出来的，按「选课（锚点未明）」处理。
3. **智能体写入已有现成机制可以复用。** 工作台已有智能体凭据（每个 agent 一个 token、按工具授权、每次调用记日志），现有 `strategy_month` 是只读工具。写入契约复用这套机制：新增一个只能「提交候选」的工具，不新造鉴权。
4. **本机环境下，权限隔离有真实边界。** 工作台只监听 127.0.0.1，有 shell 权限的本机进程，理论上能伪造任何请求。所以「确认只能在页面上点」能挡住误操作和越权调用，挡不住有意绕过。规格里如实写明这一点，再配三重保障：skill 规则禁止调用确认、服务端独立留痕、确认动作记录操作来源。
5. **服务截止期依赖的数据现在没有。** 动态 service_deadline 需要「服务类型 → 最短交付周期」，工作台没有这份数据。批 2 新增一张由常浩维护的「服务类型参数表」；没有参数时，按复审的规定保持 unknown。

### 1.4 三条新施工原则

全部接受，并给原则一补了一个可检查的写法：
- **原则一：允许未知，不许用未知掩盖分析不足。** 补充：每个 unknown 必须写明「缺什么信息、可以从哪里获得」。写不出获取途径的 unknown 视为分析不足，复审时退回。
- **原则二：促销必须交付，但不强制生成无依据的主推。**
- **原则三：方法论进化的对象是规则，不是单次文案偏好。**

## 4. 批 0 规格

### 4.1 Schema v2

#### 4.1.1 结构：五类核心对象 + 一层展示映射

```
Evidence 事实与证据 ──▶ Scenario 用户情境 ──▶ Claim 研判 ──▶ Opportunity 机会 ──▶ Strategy 方案
        └──────────────────── 引用关系全部用 ID ────────────────────┘
                                   │
                    View Projection：投影成「五大地区 + 其他 × 8 字段」和促销四部分
```

**地区不是情境。** 一个地区单元可以包含多个情境。「其他」组里的新加坡、马来西亚各自保留国家代码，不变成 other。

#### 4.1.2 统一状态

| status | 含义 | 规则 |
|---|---|---|
| `known` | 有足够证据 | 必须引用至少一个 Evidence |
| `inferred` | 有间接依据，有条件的推断 | 必须写推导规则或理由，以及限定条件 |
| `unknown` | 依据不足，暂不判断 | 必须写 `gap`（缺什么）和 `route`（从哪里获得） |
| `not_applicable` | 该字段对这个情境不适用 | 必须写原因；和 unknown 不能混用 |

**默认值是 unknown。** 需求强度、购买准备度、决策障碍，只有拿到明确依据才能赋值。

#### 4.1.5 版本、提交与评价（生命周期分离）

| 对象 | 性质 | 内容 |
|---|---|---|
| `revision` | **不可变** | 一次确认写入的完整内容 + `schema_version` + 输入指纹（时间线快照、规则版本、业务背景卡版本）+ 生成信息 |
| `submission` | 待确认状态 | AI 提交的候选，带 `base_revision`、`input_fingerprint`、`schema_version`、`idempotency_key`；不影响正式内容 |
| `review` | 追加记录 | 独立复审结论、问题清单、返修验收结果，关联到某个 revision |
| `rating` | 追加记录 | 常浩的 A–D 评价、修改原因、内容级或规则级标记 |
| `research` | 随 revision 保存 | 内部研判记录：Toulmin、被否方案、假设 |

评价和复审事后追加，不改变 revision 的内容和哈希。

#### 4.1.6 旧数据迁移（五步，可回退）

1. 冻结 Schema v2 和迁移映射表。
2. 备份全部旧数据：12 个内置 JSON + 本地已修改的月份（如 11 月）+ 本地存储状态，备份放在项目约定的证据目录。
3. 在隔离数据目录运行迁移，生成差异报告。
4. 验证：没有内容丢失；**可信度只能保持或降低，不能抬高**（原「AI 判断」迁移后是 `inferred` 或 `unknown`，不会因为落进「痛点」字段就变成「实际困难」）；「你写的」保留原样。
5. 切换正式读写路径；旧版只读存档；回退方案写成可执行的命令。

### 4.2 需求生命周期规则 `lifecycle-v0.1`

#### 4.2.1 五字段

| 字段 | 定义 |
|---|---|
| `event_date` | 时间锚点：官方确认或有效推测的事件时间 |
| `need_window` | 该事件可能引发相关学业需求的候选区间 |
| `action_window` | 学生适合开始安排相关支持的候选区间 |
| `service_deadline` | 具体服务仍有合理交付价值的条件；动态计算，不按事件类型写死 |
| `next_stage` | 事件之后可能衔接的下一项学业任务（状态转换，不是时间窗口） |

#### 4.2.2 八类事件初值

以下是**候选启发式参数**，用于方法论试运行，不是已验证的需求规律，也不是购买概率或触达规则。T 为锚点日期。

| 事件类型 | need_window | action_window | next_stage |
|---|---|---|---|
| Final | T-42 至 T-1 | T-28 至 T-5 | 出分、学期衔接、可能的补考 |
| 期中 | T-28 至 T-1 | T-21 至 T-3 | 课程后续任务、Final |
| Essay / Report 截止 | T-28 至 T-1 | T-21 至 T-3 | 后续作业、反馈、考试 |
| 补考 | 公告后至 T-1，回看不超过 28 天 | 公告后至 T-3，按实际剩余时间调整 | 出分、后续修课 |
| 出分 | T 至 T+14 | T 至 T+10 | 复盘、补考或新学期规划 |
| 选课截止 | T-30 至 T-1 | T-21 至 T-2 | 课程确认、开学准备 |
| 开学 | T-45 至 T+14 | T-30 至 T+7 | 课程适应、第一次重要考核 |
| 假期 | 不默认推出独立辅导需求 | 不默认设置购买行动窗 | 视下学期或其他真实任务而定 |

#### 4.2.3 解释规则

1. 需求窗口和行动窗口可以重叠。
2. 补考必须考虑实际通知时间；不知道公告时间时，只按考试日期形成暂定候选窗口，不把通知日期当成事实。
3. 出分是新的需求起点，但不假设所有学生都需要其中某一种服务。
4. 选课必须明确锚点（开始 / 正常截止 / 补退选截止）。时间线分不出锚点时，标「选课（锚点未明）」，窗口 status 为 inferred。见 1.3 第 2 条。
5. 假期是情境因素，只有和开学、预习、考试等具体任务形成联系时，才产生机会。

#### 4.2.4 工程规则

| 场景 | 处理 |
|---|---|
| 只有月份，没有具体日期 | 保留月度需求可能，不补成某一天，不计算窗口 |
| 同一事件有多份校历，或日期冲突 | 用已裁定或官网核实的版本；没有裁定就保留不确定性，窗口标 inferred |
| 考试持续多天 | 区分开始和结束；Final 默认以开始日为锚点，出分以结束日为参照 |
| 学校覆盖不完整 | 写明数据覆盖率；「没有记录」不等于「没有需求」 |

每个窗口都带 `ruleVersion` 和 `status`。默认参数只能通过 refine 流程修改，AI 不在单月里自行改天数。对某个地区或学校的单次调整，写进 Claim 的理由里，不改规则。

### 4.3 障碍体系 v2 与促销目标

#### 4.3.1 障碍体系

- `barrier_taxonomy_v2`：新方法论使用的完整购买障碍体系，新签、续费都覆盖，允许增补。
- `legacy_barrier_code`：与旧 A1–C1 的映射，供 47 张卡继续关联；新障碍映射不到旧编号时为空，不强行归类。
- 批 0 交付 v2 草案。方向是保留 A1–C1 的语义，新增续费类（如上阶段体验一般、下阶段没有明确任务、导师不匹配、课时没用完）和产品适配类（如现有方案不匹配学生的任务）。

#### 4.3.2 促销目标的得出

```
用户机会 + 决策障碍 + 用户阶段（新签 / 续费）→ 候选促销目标（1–3 个）→ 研判选定 → 候选打法
```

- 映射表只给候选，最终目标要经过研判和论证。例：「不信任效果」可以对应「信任建立」，也可以对应「降低行动门槛」，取决于情境和产品条件。
- 同一张卡可以服务多个目标，方案里必须写明主要目标。

#### 4.3.3 基线对照

- `matchPromo` 冻结为 `baseline-v1`（版本号写进代码和输出），之后不再修改。
- 新方案与基线的差异，按复审分四类处理：

| 差异类型 | 处理 |
|---|---|
| 新增时间限制排除了旧打法 | 写明新规则为什么排除 |
| 新签、续费独立判断 | 写明新的用户依据 |
| AI 提出更优候选 | 比较目标匹配、证据和适用条件 |
| 旧数据无法映射到新结构 | 标「不可比较」，不强行解释 |

### 4.4 会话运行与写入契约

#### 4.4.1 流程

```
Claude / Codex 会话运行 skill
  → 读：strategy_month、时间线事实、生命周期窗口（现有只读工具 + 新增只读接口）
  → 提交：strategy_submit（新增，只能创建 submission）
  → 工作台：结构校验、来源版本核对、促销适用性校验、与当前 revision 的差异
  → 常浩在页面上预览并确认 → 生成新 revision
```

#### 4.4.2 四项硬约束

| 约束 | 做法 |
|---|---|
| 权限隔离 | 智能体凭据只授权 `strategy_submit` 这类提交工具；确认接口不在智能体工具里，只供页面调用，并要求同源 Origin。skill 规则明确禁止调用确认接口 |
| 来源版本绑定 | 提交必须带 `base_revision` + `input_fingerprint` + `schema_version`；确认时任一项和当前不一致，就要求重新预览，不静默覆盖 |
| 幂等与冲突 | 同一 `idempotency_key` 重复提交返回同一个 submission；常浩在提交之后改过内容的，旧 submission 失效 |
| 可信留痕 | AI 自报的执行方、模型只作「声明」；服务端独立记录提交时间、智能体身份（来自凭据）、确认时间和确认来源 |

**真实边界**：工作台只监听本机。有 shell 权限的本机进程能伪造请求，以上措施能防误操作和越权调用，防不了有意绕过。单人本机使用时，这个风险可以接受，规格里如实记录。

#### 4.4.3 人工修改保护

- refresh 只修订「依赖的 Evidence 已变化」的 Claim，以及由它派生的 Opportunity 和 Strategy。
- 「你写的」内容永不自动改写；它依赖的证据变了，只标「依据已变化，请核对」。
- 每次 refresh 的提交都附「受影响对象清单」。

#### 4.4.4 与全局规则第 14 条（AI 接入）的关系

第一、二批工作台不调用模型，属于「MCP 开放 / 接口写入」。`AGENTS.md` 新增「AI 接入」一节：写明谁能提交、能写什么、在哪里关掉（撤销凭据），以及留痕字段。页面上每份 revision 显示执行方声明和服务端记录。

### 4.5 月度业务背景卡

| 字段 | 内容 | 允许留空 |
|---|---|---|
| 本月重要变化 | 相较上月，业务上值得注意的变化 | 是 |
| 用户观察 | 咨询热点、典型问题、已观察到的需求 | 是 |
| 存量用户情况 | 老学员下一阶段任务、续报要关注的问题 | 是 |
| 产品与资源约束 | 可用产品、重要师资限制、既定活动 | 是 |
| 负责人特别判断 | 本月最关心、希望 AI 深入检验的问题 | 是 |

- **每条内容标证据类型**：事实记录（有可核实记录，可作 Evidence）、业务观察（经验性判断，可作 inferred 的依据）、管理判断（负责人假设，不能直接认定为已验证障碍）。各自附来源或一句依据。
- **AI 先预填**：以上月的卡和本月时间线变化为底稿，常浩只补充或纠正。
- **缺失时降级**：「存量用户情况」为空时，续费的情境、障碍一律为 unknown，续费促销只出「候选待确认」，并写明需要什么信息。

### 4.6 验收标准

| 关口 | 标准 |
|---|---|
| 技术试跑 | Schema v2 校验、事实追溯、结构校验、回归测试全部通过；常浩评级至少 C |
| 正式内容 | 重要事实正确、关键推断有依据、主要需求覆盖完整；常浩评级**至少 B** |
| 追溯 | 所有影响 P0 / P1 机会的结论，都能追溯到具体 Evidence 或明确标注的假设 |
| 独立复审 | 复审方拿到五项输入：正式稿、结构化研判记录、关键事实与来源引用、方法论与质量标准、规则和数据版本；不给生成过程。轮次固定为「一次全面复审 → 一次针对性返修验收 → 未解决的关键问题交常浩裁决」 |
| 复审能力评测 | 预先注入缺陷的样例（日期错误、逻辑跳跃、错误的促销映射等），复审要能发现；无缺陷样例，复审不能无依据地挑错 |
| 两次可比实跑 | 2026-12 和 2027-01 用同一 skill 版本、同一规则版本走完整流程，保留输入、版本和审核证据；用于判断 my-skills 立项 |
| refine | 验收的是「能否正确判断有没有必要修改」：可以产出有案例和论证的提案，也可以如实写「本月未发现需要修订的通用规则」 |

### 4.7 自进化边界

```
反馈 → 问题分类（内容级 / 规则级）→ 规则修订候选 → 基准案例复验（新旧结果对比）→ 常浩批准 → 升规则版本
```

- 内容级反馈只改本月策略。
- 规则级反馈才进 refine。例：「这类用户不该归为没有购买意愿，因为我们根本没有相关证据」属于规则级。
- 不强制每月产生提案；稳定运行也是能力。
- 任何规则升级，都要在基准案例上比较新旧结果，不能只看新规则的表述。
