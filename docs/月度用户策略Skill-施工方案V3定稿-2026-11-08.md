### 1.2 我补充的 3 处（复审没覆盖，来自现有代码）

1. **单元格地址不适合做身份。** 定向复审建议用「来源表、年份、单元格、片段」定位事件。但飞书表一旦插入行或列，单元格地址就整体平移（如 S12 变成 S13），同一事件会被当成新事件。现有解析已经按「学校 + 列名 + 同名列序号」给每格分槽（`timeline.mjs` 里的 `${列名}|${序号}`）。所以 `evidenceId` 改用语义定位：年份 + 地区表 + 学校 + 列名与序号 + 片段身份。单元格地址只作为溯源字段，不参与身份计算。
2. **证据强度需要可判定的分级标准。** 只写一个 `evidenceStrength` 字段，AI 会凭感觉填。本版给出四级标准，并规定它和 status 的绑定关系（4.1.2）。
3. **「不许编造来源」需要能检查。** 新增一张「来源登记表」，列出所有已知数据来源及其可用状态。unknown 的 route 只能指向登记表里的来源，或标为「需新调研」；指向登记表以外来源的，复审直接退回（4.1.2）。

## 4. 批 0 规格

### 4.1 Schema v2

#### 4.1.1 结构

```
Evidence 事实与证据 ──▶ Scenario 用户情境 ──▶ Claim 研判 ──▶ Opportunity 机会 ──▶ Strategy 方案
                         （引用关系全部用 ID）
                                   │
              View Projection：投影成「五大地区 + 其他 × 8 字段」和促销四部分
```

地区不是情境。一个地区单元可以包含多个情境；「其他」组里的新加坡、马来西亚各自保留国家代码。

#### 4.1.2 状态、证据强度与未知

**status**（判断状态）：

| status | 含义 |
|---|---|
| `known` | 有足够证据，可以作出判断 |
| `inferred` | 有间接依据，作有条件的推断 |
| `unknown` | 依据不足，暂不判断 |
| `not_applicable` | 该问题对这个情境不适用 |

**evidenceStrength**（证据强度，四级）：

| 级别 | 判定标准 | 典型来源 |
|---|---|---|
| `strong` | 直接证据，且适用对象匹配 | 官网核实或人工裁定的日期；有可核实记录的业务事实 |
| `partial` | 间接证据，或样本有限、未经核验 | 业务观察；飞书原表未核实的日期；单一来源 |
| `weak` | 只有常识推断或类比 | AI 依据规律推断；参照往年 |
| `none` | 没有证据 | — |

**绑定规则**：
- `known` 必须是 `strong`。
- `inferred` 必须是 `partial` 或 `weak`，并写 `limitations`。
- `unknown` 对应 `none` 或 `weak`，并写 `gap` 和 `route`。
- `not_applicable` 必须写原因。

**unknown 的 route**（定稿规则：必须说明信息缺口，并交代获取途径是否可行；可以写「目前不可取得」，不能编造来源）：

```jsonc
{ "status": "unknown", "evidenceStrength": "none",
  "gap": "缺少目标学生真实未购原因",
  "route": { "status": "available|unavailable|research",
             "source": "SRC-crm",                    // 必须是来源登记表里的 ID，research 时可为空
             "suggestion": "后续接入销售未购原因记录",
             "reason": "当前尚无对应数据接口" } }
```

| 情况 | 处理 |
|---|---|
| 缺少信息，但有明确来源 | `route.status=available`，写可执行的获取方式 |
| 来源目前无法访问 | `route.status=unavailable`，写原因 |
| 需要额外调研 | `route.status=research`，写建议的验证路径 |
| 来源已有，但 AI 没有检索 | 属于分析不完整，复审退回 |
| 问题本身不适用 | 用 `not_applicable`，不用 unknown |

**来源登记表**（批 0 定稿初版，之后随接入情况更新）：

| ID | 来源 | 当前状态 |
|---|---|---|
| SRC-timeline | 飞书时间线（含官网核验、人工裁定） | 可用 |
| SRC-bizcard | 月度业务背景卡 | 可用（可选） |
| SRC-playbook | 打法库 47 张卡 | 可用 |
| SRC-voice | Voice 留学之声原声 | 不可用（未接入） |
| SRC-crm | 销售 / 咨询 / 未购原因记录 | 不可用（未接入） |
| SRC-service | 服务类型参数表 | 不可用（批 2 建立） |

#### 4.1.3 对象定义

**Evidence**：由工作台代码生成，skill 只引用。

```jsonc
{ "evidenceId": "EV-<指纹>",        // 身份：年份 + 地区表 + 学校 + 列名与同名序号 + 片段身份；不含单元格地址和原文
  "evidenceVersion": "<指纹>",      // 版本：有效起止日期 + 事件类型 + 锚点类型 + 适用对象 + 核验状态 + 原列名
  "kind": "timeline|official|ruling|business|voice",
  "country": "uk", "school": "爱丁堡大学", "header": "Term 1 结束", "eventType": "结课",
  "anchorType": "start|end|deadline|release|anchor_unknown",
  "dates": { "from": "2026-12-04", "to": "2026-12-04", "precision": "day|month|none" },
  "verification": "verified|ruled|source|guess|conflict",
  "ambiguous": false,               // 同一格多段重排、拆分、合并，无法和旧片段对应时为 true，并生成新 ID
  "source": { "ref": "英国 爱尔兰!S12", "raw": "原文", "snapshot": "<时间线快照指纹>" } }
```

- **片段身份**：一格只有一段，就是这一格；多段时，用片段标签（如「T1」「Semester 2」）定位，没有标签才用序号。新旧片段数量或标签不一致时，标 `ambiguous`，不复用旧 ID。
- **依赖检查以 `evidenceVersion` 为准**：版本变了，引用它的 Claim 就标「依据已变化」。这覆盖了定向复审举的两种情况：原格不变但官网核实日期变了（版本变、ID 不变）；原格措辞改了但事件不变（ID 不变，有效内容没变则版本也不变）。
- **官网核验和人工裁定的记录键**（含异常描述的指纹）保持原样，不和 `evidenceId` 混用。两者是不同的标识：核验和裁定的结果，以「核验状态」和「有效日期」进入 `evidenceVersion`。

**Scenario**：

```jsonc
{ "id": "SCN-2026-12-uk-01", "region": "uk", "countries": ["uk"], "schools": ["…"],
  "academicStage": "undergraduate", "phase": "Term 1 结课与作业",
  "targetRelation": "新签|续费|通用",          // 策略面向的人群：一种研究设定，不代表已掌握真实人数或购买状态
  "observedRelation": { "value": "新签|续费|unknown", "evidenceRefs": [] } }
                                              // 经证据支持的用户关系：只接受业务记录类证据；时间线事件不能作依据
```

**Claim**：只用于会影响机会和促销的实质判断。

```jsonc
{ "id": "CLM-…", "scenario": "SCN-…",
  "claimType": "task|academic_need|pain|need_strength|readiness|barrier",
  "painKind": "typical|observed",               // 仅 pain：典型困难 / 已被反馈、诊断或记录观察到的实际困难
  "text": "部分目标学生可能需要期末复习规划",
  "status": "inferred", "evidenceStrength": "weak",
  "evidenceRefs": ["EV-…"], "rule": "lifecycle-v0.1/final", "dependsOn": [],
  "limitations": "尚缺咨询或学情诊断证据",
  "gap": null, "route": null,                   // status=unknown 时必填
  "barrierCode": null, "legacyCode": null }     // 仅 barrier，见 4.3
```

页面上的「客观任务 / 潜在需求 / 已验证需求」不再存储，由展示层推导：
- `task` + `known` → 客观任务。
- `academic_need` + `known` + `strong`，且证据来自业务记录或原声 → 已验证需求；否则显示为潜在需求。

**Opportunity / Strategy**：沿用 V2 定义。其中 Opportunity 带 `targetRelation`，Strategy 的 `audience.relation` 改为 `targetRelation`。

```jsonc
{ "id": "OPP-…", "priority": "P0|P1|P2", "targetRelation": "新签", "scenarios": [], "claims": [],
  "window": { "from": "…", "to": "…", "basis": ["EV-…"], "status": "known|inferred" },
  "rationale": "…", "toulmin": { /* 仅 P0、P1 必填六要素 */ } }

{ "id": "STR-…", "audience": { "regions": [], "scenarios": [], "targetRelation": "新签" },
  "opportunityRefs": [], "promotionGoal": "信任建立", "playbookCardRefs": ["P0602"],
  "window": {}, "eligibility": "…", "constraints": "…", "evidenceRefs": [], "rationale": "…",
  "alternatives": [["P0201", "考试只剩 6 天，不在早鸟适用窗口"]],
  "status": "推荐|附条件推荐|候选待确认|不采用", "signals": "看到什么加码、看到什么撤回" }
```

#### 4.1.4 不变量（校验代码逐条实现，违反即拦截）

1. `known` ⇒ `evidenceStrength=strong` 且 `evidenceRefs` 非空。
2. `inferred` ⇒ `evidenceStrength ∈ {partial, weak}` 且 `limitations` 非空。
3. `unknown` ⇒ `gap` 非空、`route.status` 有值；`route.source` 非空时必须在来源登记表里。
4. `observedRelation.value ≠ unknown` ⇒ `evidenceRefs` 中至少一条的 kind 是 `business`。
5. Claim 引用的 Evidence，其 `evidenceVersion` 和提交时记录的版本不一致时，状态自动转为「依据已变化」，不能直接进入新 revision。
6. Evidence 满足 `precision ≠ day`、`verification=conflict` 或 `anchorType=anchor_unknown` 三者之一时，不生成精确窗口（见 4.2.4）。
7. Strategy 为「推荐」⇒ 引用的 Opportunity 是 P0 或 P1，且对应的障碍 Claim 不是 unknown。障碍是 unknown 的，最多只能是「候选待确认」。
8. 「你写的」内容不会被 submission 自动改写。
9. revision 一经写入就不可修改；review、rating 只能追加。
10. 新加坡、马来西亚等国家，在 Evidence 和 Scenario 里保留原国家代码。

#### 4.1.5 展示映射

| 页面字段 | 来源 |
|---|---|
| ① 用户情境 | 该地区的 Scenario（显示目标人群；关系有证据时另外标出） |
| ② 关键节点 | 被引用的 Evidence，按锚点排序 |
| ③ 待办任务 | `claimType=task` |
| ④ 核心痛点 | `claimType=pain`，显示典型困难或实际困难 |
| ⑤ 需求状态 | `need_strength` + `readiness`，unknown 照实显示 |
| ⑥ 决策障碍 | `claimType=barrier`，按新签、续费分组 |
| ⑦ 机会点 | Opportunity |
| ⑧ 研判依据 | 以上对象的 evidenceRefs、rule、limitations、gap，折叠显示 |

#### 4.1.6 版本、提交与评价

| 对象 | 性质 | 内容 |
|---|---|---|
| `revision` | 不可变 | 完整内容 + `schema_version` + 输入指纹（时间线快照、引用的 evidenceVersion 清单、规则版本、业务背景卡版本）+ 生成信息 |
| `submission` | 待确认 | 带 `base_revision` + `input_fingerprint` + `schema_version` + `idempotency_key`；不影响正式内容 |
| `review` | 追加 | 复审结论、问题清单、返修验收结果 |
| `rating` | 追加 | A–D 评价、修改原因、内容级或规则级标记 |
| `research` | 随 revision | Toulmin、被否方案、假设 |

### 4.2 需求生命周期规则 `lifecycle-v0.1`

#### 4.2.1 五字段

`event_date`（时间锚点）、`need_window`、`action_window`、`service_deadline`（动态条件）、`next_stage`（状态转换）。

#### 4.2.2 八类事件初值（候选启发式参数，不是已验证的规律）

| 事件类型 | need_window | action_window | next_stage |
|---|---|---|---|
| Final | T-42 至 T-1 | T-28 至 T-5 | 出分、学期衔接、可能的补考 |
| 期中 | T-28 至 T-1 | T-21 至 T-3 | 课程后续任务、Final |
| Essay / Report 截止 | T-28 至 T-1 | T-21 至 T-3 | 后续作业、反馈、考试 |
| 补考 | 公告后至 T-1，回看不超过 28 天 | 公告后至 T-3，按实际剩余时间调整 | 出分、后续修课 |
| 出分 | T 至 T+14 | T 至 T+10 | 复盘、补考或新学期规划 |
| 选课截止 | T-30 至 T-1 | T-21 至 T-2 | 课程确认、开学准备 |
| 开学 | T-45 至 T+14 | T-30 至 T+7 | 课程适应、第一次重要考核 |
| 假期 | 不默认推出独立辅导需求 | 不默认设置购买行动窗 | 视真实任务而定 |

#### 4.2.3 解释规则

1. 需求窗口和行动窗口可以重叠。
2. 补考必须考虑实际通知时间；不知道公告时间时，只形成暂定候选窗口。
3. 出分是新的需求起点，但不假设所有学生需要同一种服务。
4. 选课必须明确锚点（开始 / 正常截止 / 补退选截止），按原列名判断；判断不了的标 `anchor_unknown`。
5. 假期是情境因素，只有和具体任务有联系时才产生机会。

#### 4.2.4 窗口生成条件（按日期确定性区分）

| 日期情况 | 处理 |
|---|---|
| 确定日期（原表、官网核实或人工裁定） | 计算窗口，status=`known` |
| 明确的推测日期（原表标为推测，但有具体日期） | 计算候选窗口，status=`inferred`，带假设标识 |
| 只有月份 | 不计算精确窗口，只保留「该月可能有需求」 |
| 锚点类型不明（`anchor_unknown`） | 不套用任何锚点规则；等补充来源，或改为不带具体日期的月度研判 |
| 多个冲突日期，尚未裁定 | 不输出单一精确窗口，等待裁定；必要时只保留覆盖全部候选日期的宽泛风险区间，标为「冲突未决」 |
| 出分 | 以实际成绩发布时间为准，不从 Final 结束日期推导 |
| 考试持续多天 | Final 以开始日为锚点；其他策略需要以结束日为锚点时，须写明 |
| 学校覆盖不完整 | 写明覆盖率；「没有记录」不等于「没有需求」 |

每个窗口都带 `ruleVersion` 和 `status`。默认天数只能经 refine 流程修改；单个地区或学校的调整，写进 Claim 的理由里，不改规则。

#### 4.2.5 service_deadline

由「学业事件 + 服务类型 + 最低交付要求 + 可用资源」计算得出。服务类型参数表批 2 建立；在此之前一律为 unknown，`route.status=unavailable`，`source=SRC-service`。

### 4.3 障碍体系 v2 与促销目标

- `barrier_taxonomy_v2`：新签、续费都覆盖的完整障碍体系，允许增补。
- `legacy_barrier_code`：与旧 A1–C1 的映射，新障碍映射不到时为空。
- 促销目标的得出：用户机会 + 决策障碍 + 用户阶段（targetRelation）→ 候选目标（1–3 个）→ 研判选定。映射表只提供候选。
- `matchPromo` 冻结为 `baseline-v1`。差异按四类处理：新增时间限制、新签和续费独立判断、AI 提出更优候选、无法映射时标「不可比较」。基线只作参照。

### 4.4 会话运行与写入契约

**安全目标**（采用定向复审原文）：在单用户可信本机环境中，阻止默认智能体工具误操作，提供提交与确认的流程隔离，保留可审计记录；不声称可以防御拥有同一用户环境下任意本地执行权限的恶意进程。

**流程**：

```
会话运行 skill → 读（strategy_month 等只读工具）
  → strategy_submit（只能创建 submission）
  → 工作台校验（结构、不变量、来源版本、促销适用性、与当前 revision 的差异）
  → 常浩在页面上预览、确认 → 生成新 revision
```

| 约束 | 做法 |
|---|---|
| 流程隔离 | 智能体凭据只授权提交类工具；确认接口不在智能体工具里，只供页面调用。同源校验只是浏览器请求的安全措施，不是身份认证 |
| 来源版本绑定 | 确认时，`base_revision`、`input_fingerprint`、`schema_version` 任一项不一致，就要求重新预览 |
| 幂等与冲突 | 同一 `idempotency_key` 只生成一个 submission；常浩在提交后改过内容的，旧 submission 失效 |
| 可信留痕 | AI 自报的执行方、模型只作声明；服务端独立记录提交时间、凭据对应的智能体、确认时间和确认来源 |
| 人工修改保护 | refresh 只修订依赖版本已变化的 Claim 及其派生对象；「你写的」永不自动改写 |

**测试**（不代表已实现对任意本地进程的强隔离）：
1. 未经确认，不能修改正式 revision。
2. 只持有提交权限的智能体凭据，调用不了确认操作。

`AGENTS.md` 新增「AI 接入」一节，内容包括：谁能提交、能写什么、在哪里关掉（撤销凭据），以及留痕字段。

### 4.5 月度业务背景卡

五个字段，都允许留空：本月重要变化、用户观察、存量用户情况、产品与资源约束、负责人特别判断。

- 每条内容标证据类型：事实记录（`strong`，可作 business 类 Evidence）、业务观察（`partial`）、管理判断（`weak`，不能认定为已验证障碍）。各自附来源或一句依据。
- AI 先以上月的卡和本月时间线变化为底稿预填，常浩补充或纠正。
- 「存量用户情况」为空时，续费的情境关系和障碍都是 unknown（`source=SRC-bizcard`，`route.status=available`），续费促销只出「候选待确认」。

### 4.6 验收标准

| 关口 | 标准 |
|---|---|
| 技术试跑 | Schema v2 校验、不变量、事实追溯、回归测试全部通过；常浩评级至少 C |
| 正式内容 | 重要事实正确、关键推断有依据、主要需求覆盖完整；常浩评级至少 B |
| 追溯 | 所有影响 P0 / P1 机会的结论，都能追溯到具体 Evidence 或明确标注的假设 |
| 独立复审 | 复审方拿到五项输入：正式稿、结构化研判记录、关键事实与来源引用、方法论与质量标准、规则和数据版本；不给生成过程。轮次为「一次全面复审 → 一次返修验收 → 未解决的关键问题交常浩裁决」 |
| 复审能力评测 | 预先注入缺陷的样例要被发现；无缺陷样例不能被无依据地挑错 |
| 两次可比实跑 | 批 2 完成后，连续两个目标月用同一 skill 版本、同一规则版本走完整流程，保留输入、版本和审核证据；用于判断 my-skills 立项 |
| refine | 能正确判断有没有必要修改：可以产出有案例和论证的提案，也可以如实写「本月未发现需要修订的通用规则」 |

**实跑时点规则**：
- **前瞻实跑**：在目标月策略发布之前完成，使用当时可得的输入。可以算作正式验收。
- **历史回放**：目标月已过，或晚于真实发布时间。只能用当时时点的输入快照（时间线快照、业务背景卡版本），不得混入事后核验的日期、事后反馈和不属于当时的业务信息。必须标注「历史回放」，只用于基准评测，不能冒充前瞻发布。
- **人工稿与 skill 稿分开**：skill 先独立生成，再和人工稿比较；人工稿只用于事后评价，不作为生成输入。

### 4.7 自进化边界

```
反馈 → 问题分类（内容级 / 规则级）→ 规则修订候选 → 基准案例复验（新旧结果对比）→ 常浩批准 → 升规则版本
```

内容级反馈只改本月；规则级反馈才进 refine。不强制每月产生提案。任何规则升级都要在基准案例上比较新旧结果。
