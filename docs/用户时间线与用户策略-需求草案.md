来源中的具体发现及需求影响：

- 国家表存在明确日期、月份级日期、开口区间，以及“去年”“预估”“推测”“AI 预测”等备注。日期精度和可信状态必须保留，不能一律转成已确认的精确日期。
- 月度表一个格子可能包含多所学校、多个事件；跨月事件也会显示在起点或终点所在日期。不能只把格子位置当作完整事件时间。
- 英国爱尔兰样本中存在日期位置出现非日期文本、区间年份前后不一致的情况。应显示待核对项，不能静默猜测或纠正。
- 月度图例的颜色分组不足以覆盖全部国家／地区。国家、地区、院校要依赖明确映射，不能只按颜色归类。
- 历史策略不只依赖时间，还使用经营数据、渠道判断、转化环节和产品条件。时间节点可以提示可能需求，但不足以单独证明痛点、购买意愿、市场规模或策略收益。

以上是输入样本的发现，不构成对整套时间线准确性的审计，也不表示本轮已把它设为正式工作台来源。

## 3. 建议的业务关系

主线：源数据中的时间节点 → 目标客群及处境 → 用户需求与痛点 → 机会判断与取舍 → 策略及业务动作 → 月度策略方案。

两部分共用同一批时间依据：时间线回答“谁、什么时候、面临什么节点”；用户策略回答“这意味着什么、值得解决什么、公司应如何行动”。切换视图不应产生另一套独立维护的日期。

需要分开保留三层内容：

1. **源事实和状态**：源表实际写了什么、适用于谁、时间是否明确、是否仍待核验。
2. **分析判断**：可能的需求、痛点、风险、机会；分别标记已有业务证据、历史经验和待验证假设。
3. **用户决策**：常浩选择的优先级、方案、资源取舍与执行动作。AI 建议不等同于已采纳的业务决定。

## 4. 用户时间线的需求展开（建议，待整体校准）

### 4.1 月度视图

- 选择年份和月份，横向了解不同国家／地区的主要节点；可筛选院校、学生阶段和节点类型。
- 月历承接现有使用习惯；节点较多时仍能看到清晰摘要并展开详细列表，不把所有信息挤进日期格。
- 区分开学、选课、考试、补考、出分、结课、假期等类型；类型范围以实际来源和业务需要为准。
- 跨月事件在所涉及月份保持可见，展开后显示完整起止时间与来源；同一事件不因跨月显示而成为多条独立事实。
- 仅知道“某月上旬”的节点按原有精度展示；不人为补成某一天。没有数据的国家应显示覆盖不足，而不是“没有节点”。

### 4.2 国家／地区视图

- 选择国家／地区与年份，沿月份查看全年或选定时段的节点与变化。
- 保留院校、校区、学制、学生阶段等适用范围；没有的字段显示未知，不强制编造。
- 可以从国家概览逐步看到学校详情，避免把少数学校的日期概括为全国统一时间。
- 学年可能跨自然年；2025 年历史参考不能自动平移成 2026 年日期。

### 4.3 每个节点需要表达的信息

建议包含：节点名称／类型、国家／地区、院校及适用客群、年份或学年、起止日期与精度、原文、来源定位、来源版本或读取时间、核验状态及备注。这是业务信息要求，不是数据库列定义。

“事件发生时间”与“公司需要提前准备的时间”分开。提前多久准备由策略决定，不改写学校的原始日期。

### 4.4 搜索与提问

- 搜索：按学校简称／全称、国家、月份、事件类型定位节点。
- 事实提问示例：“7 月哪些院校有补考？”“英国接下来两个月有哪些明确的考试节点？”
- 策略提问示例：“围绕这些节点，哪些需求值得优先验证？”“下月营销、产品、运营分别要提前准备什么？”
- 回答注明筛选范围、年份、来源与未覆盖内容；可回到相关原文。估计日期必须带原有不确定性。
- 策略回答单独显示推断依据和缺失证据，不把“有考试”直接等同于“强烈购买意愿”，不凭节点数量生成销量或收入预测。
- 默认先围绕用户提供和明确纳入的资料回答。是否扩展到学校官网研究、经营数据或咨询记录，属于后续范围决定。

## 5. 用户策略的需求展开（建议，待整体校准）

策略组织可同时保留“月度总策略”和“国家／客群策略”。总策略用于取舍与资源分配，客群策略说明具体处境和动作；两者互相关联，避免只有分散的卡片或一篇无法追溯的长文。

| 思考板块 | 要回答的问题 | 需要保留的依据或结果 |
|---|---|---|
| 目标与适用范围 | 本月支持什么业务决策？针对哪些国家、院校和学生阶段？ | 业务目标、范围、约束与缺项 |
| 时间与用户处境 | 用户正在经历什么、何时发生、紧迫性如何？ | 关联节点及日期可信状态 |
| 用户任务、需求与痛点 | 用户要完成什么？困难在哪里？我们知道还是推测？ | 学生待办、需求、痛点及证据／假设 |
| 机会与优先级 | 哪些问题值得先解决？为什么暂缓其他问题？ | 价值、紧迫性、证据、服务能力和资源限制；不默认自动打分 |
| 策略选择 | 提供什么价值？通过什么产品、服务、内容或渠道回应？ | 候选方案、取舍理由、已采纳决定 |
| 团队执行 | 营销、产品、运营各做什么，何时完成、依赖谁？ | 公司动作、负责人、期限、交付物、前后依赖；未明确项保留待定 |
| 验证与复盘 | 如何知道判断成立、行动有效？什么结果会促使调整？ | 验证信号、结果记录、待验证假设及调整条件 |

关键区别：**学生待办**例如复习、选课、准备补考；**公司动作**例如准备课程、安排师资、制作内容、组织触达。二者有关联，但不能合并为一张没有责任对象的待办清单。

建议支持用户补充、修改、采纳或拒绝分析建议，并保留自己的取舍理由。具体 AI 交互方式与保存机制后续再定，不由本草案锁定。

对于缺少经营、咨询或调研数据的情况，可以先形成带假设的讨论稿；不能把历史策略自动升级为当期结论，也不能假装这些数据已经接通。

## 6. 策略方案导出（需求已确认，形式待定）

建议方案至少包含：适用月份与客群、目标、关键时间依据、需求与痛点、核心策略与取舍、团队行动、依赖与风险、验证方法、待确认事项、来源及版本日期。

- 可按一个月份导出整套方案，也可按国家／客群选取；导出粒度待确认。
- 输出应保留判断依据，不能只导出日历截图或 AI 聊天记录。
- 建议默认作为讨论稿；只有用户确定后才标为已采纳方案。导出不等于发布、下发或执行。
- 文件格式（可编辑文档、PDF、Markdown 或飞书文档）、团队使用方式和排版要求尚未确定；本轮不新增飞书写入。
- 来源后续发生变化时，建议提示相关策略待复核，不静默改写已确认或已导出的版本。

## 7. 与工作台其他想法的关系

- **活动价格测算**：后续可为策略提供价格、成本、毛利与底线约束。相关需求仍在独立草案中，成本口径和价格底线继续由用户确定；本轮不将二者自动联动列为必做项。
- **NAS 月度物料**：未来可把策略涉及的物料与营销物料入口关联。原文件留在 NAS、默认只读的方向保持；确切目录仍待提供，不作为时间线需求梳理的前置条件。
- **既有促销方案**：可作为历史参考。是否关联、怎样采纳，以及正式促销写入仍需单独定义，不把候选策略自动写成正式活动。
- **现有经营策略页**：目前是三条业务线经营数据的占位。本轮新增时间线与策略需求，不默认删除既有方向；具体导航、页面结构和技术方案按项目分工由 Claude 后续制定。

## 8. 候选验收场景（用于校准需求，不是开发派单）

1. 从同一来源选择一个月，能看清不同国家／院校的节点；切到国家视图后，同一事件的日期、适用范围和来源一致。
2. 跨月、跨年、模糊日期、预估日期及待核对数据不会被误画为已核实的精确单日节点。
3. 搜索和事实提问可追溯到源资料；无数据或证据不足时明确说明，不编造结论。
4. 选择一个客群和月份，可以形成“节点—学生任务—需求／痛点—策略—公司动作”的讨论稿，事实、推断、已采纳决定清楚分开。
5. 导出的策略方案能供常浩判断取舍，也能让营销、产品、运营理解各自行动、期限、依据和待确认项。
6. 源资料更新、读取失败或出现冲突时，保留已知状态和版本，不误报“没有节点”或悄悄替换已采纳方案。

## 9. 待后续收敛的事项

已确认客群共性节点和月度业务决策用途，不重复询问。以下不是本轮要求用户一次提供的清单，按是否影响首版路线逐步收敛：

- 正式源范围：提供的文件只是参考，后续使用哪份、覆盖哪些业务线／国家／客群、由谁更新；国家表与月度表不一致时的权威顺序。
- 需求证据：除了时间线和历史策略，是否纳入用户补充的一线反馈、咨询记录、经营数据；只读范围与数据权限分别确认。
- 策略协作：哪些内容手动填写、哪些由 AI 辅助，如何采纳与留存；不预设自动生成即完成决策。
- 更新方式：按需刷新或其他节奏；是否保留历史快照及变更提醒。未确认前不建立定时任务。
- 导出格式、粒度与团队使用方式；本轮只确认需要导出，不选定具体格式。

本轮不做个人学生 CRM、不代替用户定策略、不自动触达或下发任务、不接新经营数据源、不修改源表或正式工作台、不创建派单或开发代码。需求整体校准后，再由 Claude 按现有分工制定页面／接口／派单；仍需另行明确开发范围。
