## 0. 结论

**方向上达成共识，可以作为施工基线。** V1.1 的定位、三重验收、地区体系、「需求不等于购买」、动态需求时间窗、「机会先于打法」、「促销必须交付」、以认知质量驱动进化，以及分三批建设，我都同意。

**有 10 条优化意见，必须在施工前落实。** 它们不推翻方法论，主要补三类缺口：

1. **输入断层**：方法论要求的证据，工作台目前拿不到。
2. **参数缺失**：给了概念，但没有可执行的规则。
3. **工程冲突**：方法论和现有系统已确定的做法不一致。

另有 **5 项需要常浩拍板**，每项都附了推荐默认值。下文的施工方案按推荐值编写。

| # | V1.1 的主张 | 和现有系统的关系 |

## 2. 优化意见（10 条）

### 意见 1 · 证据来源断层：方法论要的证据，工作台现在没有

V1.1 多处依赖「用户反馈、业务记录、已购用户名单、实际困难、已验证需求」。工作台目前**只有时间线一个事实来源**：Voice 原声没有接入，也没有任何业务数据。

如果不补输入，每个月都会出现三种情况：
- 续费独立研判没有材料。
- 「实际困难」和「已验证需求」两级永远是空的。
- 决策障碍大量写成「待确认」。

这样的策略写法严谨，但拿不出手，和「可供跨部门发布」的验收标准直接冲突。

**建议**：
- **新增「月度业务背景卡」**，作为每月可选的人工输入，常浩约 10 分钟填完：在读学员概况与下一阶段任务、上月咨询热点、本月可用产品与师资、已定的外部活动、本月特别关注点。缺了它，续费研判自动降级为「候选 + 条件」。
- **规定证据不足时怎么写才可以发布**：主张 + 限定条件 + 验证信号（看到什么就加码、看到什么就撤回）。这样即使证据不足，也是一份可执行的策略。
- Voice 原声接入放进第三批，作为「实际困难」的证据来源。

### 意见 2 · 需求生命周期只有概念，没有参数

V1.1 定义了 5 个时间字段，但没有说**每类事件的窗口具体多长**。这正是上一轮指出的缺口：「事件 → 需求」对照表一直没有成表。

**建议**：
- 建一张版本化的「需求生命周期表」，按事件类型（Final、期中、补考、出分、Essay 截止、选课、开学、假期）给出默认窗口，例如 Final 的 need_window 为考前 28–15 天、action_window 为考前 14–3 天、service_deadline 为考前 1 天。
- 代码按这张表，为每个时间线事件算出默认窗口。
- AI 可以针对具体地区或学校调整窗口，但必须写理由，并标「AI 判断」。
- 初值由 Claude 起草，常浩确认，GPT 复核。

### 意见 3 · 新增的「促销目标」层，要和现有词表、卡片对齐

V1.1 在「障碍」和「打法」之间加了「促销目标」（需求唤醒、信任建立、降低门槛、时间促进、价值增强、续费承接、扩科发展）。47 张卡目前按障碍编号打标签。

**建议**：
- 9 项障碍词表保留为受控词，卡片靠它关联。
- 允许写「待确认」。
- 增加一张**续费障碍子表**，例如：上阶段体验一般、下阶段没有明确任务、导师不匹配、课时没用完。
- 「促销目标」由障碍映射得到（障碍 → 目标是多对多的固定表），**不重新给 47 张卡打标签**。

### 意见 4 · 讲清规则匹配的去留：保留为基线对照

V1.1 第 6.4 节实际上改变了 2026-10-20 的决定：从「规则匹配、不调用模型」改为「AI 提候选，规则校验」。我同意这个改动。

**建议**：现有 `matchPromo` 不删，降级为**基线对照**。AI 方案与基线不同的地方，必须逐条解释。这正好满足第三重验收里「能解释分歧」的要求，也能防止 AI 方案偏离太远。

### 意见 5 · 限定 Toulmin 的范围，否则成本失控

如果每条判断都写满六要素，每月的研判记录会膨胀到无法审阅。

**建议**：只对「核心判断」做完整六要素：
- 核心结论
- 每个 P0、P1 机会
- 每个主推和辅助促销
- 优先级有争议的地区

其余条目只要求「依据 + 来源」。

### 意见 6 · 「独立复审」要真独立

在同一个上下文里「切换成审核视角」，效果有限，因为写的人很难看见自己的盲区。

**建议**：
- 检查 2（整份独立复审）由**新上下文的子 agent**，或**跨模型（GPT）**执行，只给它正式稿、研判记录和质量标准，不给写作过程。
- 检查 3（定向验收）由原执行方返修后，交回同一个复审方，只核上一轮指出的问题。

### 意见 7 · 基准案例库不能用现有的 12 个月起步

现有 12 个月的用户情况是 Claude 在 10-20 批量写成的，常浩没有逐月认可过，不能当高质量基准。

**建议**：首批基准用三样材料：
- 飞书《2025 大学辅导-策略文档》中常浩认可的部分。
- `docs/大学辅导用户策略-2026年10月-示例.md`。
- 新方法第一次实跑后，常浩打 A 或 B 的月份。

### 意见 8 · 数据结构是破坏性改动，要一次迁移

V1.1 落到数据层，至少有五处破坏性变化：

- 7 个地区改为 6 个：新加坡并入「其他」。
- 6 格改为 8 字段。
- 决策障碍允许为空或「待确认」。
- 障碍分新签、续费两组。
- 促销四部分重构，从「组合、逻辑、不选、底线」改为「总判断、主推、辅助与特殊、边界与不采用」。

现有 `checkInsight`、`checkPromo`、页面、接口文档、测试和 12 个月的 JSON 都要改。

**建议**：
- 定义 schema v2。
- 写一个迁移脚本，把旧数据转成 v2，旧文件保留只读。
- 新旧结构不长期并存。

### 意见 9 · 版本历史要补

V1.1 的 refresh 要求「保留人工修改和版本历史」，但现有规范写的是「不保留历史版本」，存储层也没有历史。

**建议**：每次确认写入时保存一个快照，记录时间、执行方、改动摘要。页面能看历史版本，能和当前版本对比。

### 意见 10 · Skill 的命名与立项，按 my-skills 约定走

- **命名**：V1.1 用的是 `student-strategy-intelligence`。按 my-skills 约定，建议改成短而直白的名字，例如 `monthly-user-strategy`，中文名「月度用户策略」。
- **立项闸**：my-skills 的闸 1 要求「真做过两次、走法一致」。建议用 **2026-12** 和 **2027-01** 两次真实运行满足闸 1。这两次本来就是第一批的验收。

## 4. 施工方案

### 4.1 总体分工

```
            ┌───────────── my-skills：monthly-user-strategy ─────────────┐
            │  generate / refresh / review / refine 四种模式             │
            │  SCOUT-8 流程、证据分级、Toulmin、写作规范、自检模板        │
            └──────┬───────────────────────────────▲─────────────────────┘
          读事实与规则 │                               │ 预览 → 常浩确认 → 写入
            ┌──────▼───────────────────────────────┴─────────────────────┐
            │  niuma-home（工作台）                                       │
            │  L1 时间线（不改）→ 需求生命周期计算（新）                   │
            │  schema v2 校验（改 checkInsight / checkPromo）              │
            │  促销规则校验器 + matchPromo 基线（改）                       │
            │  整月导入接口、版本历史、研判记录存储（新）                   │
            │  页面：用户洞察 8 字段、促销四部分、研判依据折叠（改）        │
            └────────────────────────────────────────────────────────────┘
```

**原则**：
- **判断归 skill**：情境、任务、困难、障碍、机会、促销方案和论证。
- **规则与校验归工作台代码**：时间线事实、生命周期窗口、结构校验、打法阶段与冲突、时间适用性。
- **写入一律先预览、后确认**，由常浩确认。

### 4.2 数据结构 v2（草案，批 0 定稿）

地区单元（6 个：uk / us / hk / au / ca / other）：

```jsonc
{
  "key": "uk", "name": "英国",
  "priority": "主战场",          // 当月策略优先级：主战场 / 次要 / 平稳
  "activity": "高",              // 当月需求活跃度：高 / 中 / 低（由生命周期窗口密度给出建议值，AI 可改并写理由）
  "contexts": [["英国本科—Term 1 结课与作业—新签", "AI 判断"]],     // ① 用户情境
  "node":    [["12/11 前 15 所结课", "时间线", ["英国 爱尔兰!S12"]]],  // ② 关键节点，可追溯到格
  "task":    [["结课前交齐 Term 1 课程作业", "客观任务", "时间线"]],   // ③ 待办任务 + 证据等级
  "pain":    [["英式学术写作不熟", "典型困难", "AI 判断"]],            // ④ 核心痛点：典型困难 / 实际困难
  "need": {                                                            // ⑤ 需求状态（取代冷 / 温 / 热）
    "academic": "高", "readiness": "中",                               // 学业需求强度、购买准备度，分开判断
    "turning": [["11/16 起作业截止临近", "规则推导"]]
  },
  "barrier": {                                                         // ⑥ 决策障碍：新签、续费分开，可为「待确认」
    "新签": [["A2", "Final 在 1 月，觉得还来得及", "AI 判断"]],
    "续费": [["待确认", "缺在读学员下阶段任务信息", "—"]]
  },
  "opp":   [["论文审读与写作 1v1 · 11/09–12/11", "AI 判断"]],           // ⑦ 机会点
  "basis": [["英国是本月主战场", "15 所结课集中在 12/11 前", "已核实"]], // ⑧ 研判依据（页面折叠显示）
  "master": []
}
```

整月文档另外新增：
- `inputs`：本月使用的时间线快照指纹、业务背景卡、生命周期表版本。
- `producedBy`：执行方、接入方式、模型、时间、skill 版本，满足留痕要求。
- `review`：自检记录，含 8 项检查结果和返修记录。
- `rating`：常浩的 A–D 评价、修改原因、内容级或规则级标记。
- `research`：内部研判记录，含 Toulmin、被否方案、假设；不在正式稿里展示。

来源标注扩充为：时间线（含官网核实 / 人工裁定）、业务记录、原声、规则推导、AI 判断、推测、你写的。

促销 v2，新签、续费各一份：
- 4.1 本月促销总判断
- 4.2 主推方案：打法、目标用户、窗口、产品方向、核心权益、对应的机会
- 4.3 辅助与地区特殊方案：附启用条件和退出条件
- 4.4 适用边界与不采用的方案：含毛利、价格锚点、合规三条底线，以及随打法变化的条款
- 另附基线对照：`matchPromo` 结果与 AI 方案的差异及解释

### 4.4 风险与应对

| 风险 | 应对 |
